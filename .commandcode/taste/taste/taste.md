# Taste
- For substantial projects, wants a careful planning phase first: read requirement/audit docs fully and carefully before writing any code, then produce an implementation plan covering the whole project. Confidence: 0.8
- Save implementation plans as markdown files inside the project's `docs/` directory. Confidence: 0.8
- After producing an implementation plan, spawn a fresh-context subagent (no prior assumptions) to read, validate, and harshly criticize the plan and propose optimizations before starting implementation. Confidence: 0.7
- Prefer giving spawned review subagents strict constraints (read-only, pure analysis, no file writes) and require a structured verdict/findings report mapping each finding to the requirement it affects. Confidence: 0.6
- After finishing implementation, use review agents to verify correctness and fullness (completeness against requirements). Confidence: 0.7
- Success criterion is audit-driven: every question in the audit must be answered correctly — prioritize completeness and correctness over speed. Confidence: 0.7
- Open to reusing/adapting public reference implementations (e.g., GitHub repos like crud-master-py) as the basis for services instead of designing from scratch. Confidence: 0.7
- Implementation plans should embed canonical/binding drafts of the most error-prone artifacts (e.g., docker-compose.yml, entrypoint/init scripts, code contracts) — prose-only design descriptions leave room for improvisation and are considered a gap. Confidence: 0.7
- Plans must contain an explicit gated validation loop (fail → fix → rerun from the earliest affected gate), verifying build outputs against requirements during implementation — not only end-of-build checks. Confidence: 0.8
- Keep the README lean — long-form learning/study content must live in separate standalone docs (under `docs/`), never embedded as a big README appendix. Confidence: 0.9
- For audited projects, split study material into two purpose-specific docs: (1) a generalized theory study guide — textbook-style theory with examples, independent of the specific implementation — and (2) an audit preparation guide — every audit question quoted verbatim and organized by section, with correct answers, explanations, required demos/commands, and extra prep for likely auditor follow-up questions. Confidence: 0.9
- For thorough verification/extraction work, spawn research agents (in parallel when their tasks are independent) and demand verbatim, complete extraction of source-of-truth content (e.g., the full audit checklist) rather than summaries. Confidence: 0.7
- When moving content out of a README into `docs/`, replace the removed section with a "Documentation Index" table (each doc + one-line purpose, with links) so the README remains the discovery hub rather than just losing the section. Confidence: 0.6
- Audit-prep answers should be evidence-backed rather than textbook-generic: cite the concrete repo artifacts that enforce each answer (exact commands with verbatim expected outputs, Dockerfile/compose/source references). Confidence: 0.6
- Finish multi-step file-producing tasks with a final verification pass (e.g., `ls`/`wc -l` over the produced files) before reporting completion. Confidence: 0.6
- When a spawned subagent runs out of context or fails mid-task, fall back to doing the verification work directly rather than abandoning it — and the direct pass can be more thorough than the subagent's. Confidence: 0.7
- Prefer programmatic verification of technical claims: Python heredoc scripts that read source files, run `re.findall`/substring checks, and emit structured `[OK]/[FAIL]` output with file:line evidence — rather than ad-hoc shell greps that have to be reasoned about one at a time. Confidence: 0.7
